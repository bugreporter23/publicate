# Private ticket backchannel

Publicate defines two public contracts: verified source publication and a private
ticket backchannel. The [publication workflow](GIT.md) maintains SemVer snapshots.
The ticket system is a repository plugin: each repository advertises its own queue,
and agents use that queue's Git permissions. Publicate's own repository uses the
same contract as every other consumer. Ticket commands also work independently of
source exporting or a publication policy, using the repository's `PUBLICATE.json`.

## Discovery and access

Exports generate root `PUBLICATE.json` by default when the project has a publishable
private Git address. The address comes from `tickets.repository`, falling back to
the private project's `origin`. HTTPS and SSH addresses are supported. Local
filesystem endpoints stay local. A source checkout with a policy uses its private
endpoint; a public consumer reads the advertised endpoint from `PUBLICATE.json`.

```json
{"schema":1,"tickets":{"repository":"git@example.org:team/project-private.git","branch":"publicate/tickets","path":"tickets","format":"publicate-tickets-v1"}}
```

The repository address is public information. Ticket records require access to
the private repository. Read and write access follow that server's Git permissions
and the invoking agent's credentials. The discovery file contains an address and
format identifiers; credentials belong to the caller's Git environment.

Configure an explicit endpoint or disable advertising in the private policy:

```toml
[tickets]
repository = "git@example.org:team/project-private.git"
advertise = true
```

`advertise` defaults to true; setting it to false omits generated discovery.
`PUBLICATE.json` is reserved for generated discovery when advertising is active.
Review this address as part of the exported content before publication.

## Ticket records and Git snapshots

The exact Git branch is `publicate/tickets`. Its tree contains only
`tickets/UUID.json` files. Initialization creates a parentless commit. Agent
submissions and review updates append ordinary commits and use fast-forward pushes.
The commit has fixed author and committer `user.name` / `user.email`, epoch timestamps
and message `publicate`. Repeating an unchanged ticket set reuses its commit ID.
Concurrent edits to separate records merge, while conflicting edits to one record
stop synchronization. Clients fetch the queue with depth 1; ticket consumption
depends on the current tree and record IDs. The repository owner periodically
compacts history. Server object retention follows ordinary Git policies.

Each record has schema 1, a UUIDv4 generated by `uuid.uuid4()`, a SHA-256 content
fingerprint, title, body, version context and status. The UUID names the record;
the fingerprint identifies its immutable report content. Repeated submissions
with the same normalized title, body and version reuse the existing ticket,
including a ticket already reviewed. New content creates a new UUID.

The fingerprint hashes UTF-8 JSON with sorted keys and compact separators,
containing exactly `title`, `body` and `version`. The JSON encoder uses Python's
default ASCII escaping. Submission strips leading and trailing whitespace from
title and body. Filenames must match the record's canonical lowercase UUIDv4.

Required fields are `schema`, `id`, `fingerprint`, `title`, `body`, `version`,
and `status`. Status is `open`, `applied` or `inapplicable`. Optional fields are
`resolution` and `reviewed_version`. A resolved record requires a concrete
resolution. The title, body, version, ID and fingerprint remain fixed during
review. `version` can hold a public release label or an empty string; the review
records which current source version was evaluated.

Publicate excludes `tickets/`, the project `publicate/` directory, and files named
`publish.sh` or `review.sh` from source exports, including explicit remaps.
The ticket branch belongs to the private endpoint. Public source publication and
private ticket publication each update their own explicitly selected refs.

## Report an issue

With Git and a Publicate app available, create a report in a fresh temporary
directory. From a public checkout containing discovery, use an installed
`publicate` command:

```sh
report_dir=$(mktemp -d "${TMPDIR:-/tmp}/publicate-ticket.XXXXXX")
printf '%s\n' 'Describe the reproducer, expected result and observed behavior.' > "$report_dir/body.txt"
publicate ticket --title 'Terminal input stops after reconnect' \
  --body-file "$report_dir/body.txt" --code-version v0.1.4 --push
```

From a private project with a `publicate` Nix app, the equivalent command is
`nix run .#publicate -- ticket ...`. `--repository URL` explicitly selects a private
endpoint. Omit `--push` to keep the record in the local ticket branch.
The result reports the UUID and commit. The caller's source checkout and index
remain available for ordinary development.
Submissions save the ticket locally before contacting the private endpoint.
Authentication or access failures retain that record. Use the existing SSH agent
and Git credentials; an unlock, host verification or access request is a routine
human handoff. Explain the required step and retry the same submission once access
is ready. Review files likewise remain available after failed synchronization.

To pull just the queue using ordinary Git, choose a fresh destination:

```sh
queue_dir=$(mktemp -d "${TMPDIR:-/tmp}/publicate-queue.XXXXXX")
git clone --depth 1 --single-branch --branch publicate/tickets \
  git@example.org:team/project-private.git "$queue_dir/queue"
```

The checkout contains ticket records. A repository's public `PUBLICATE.json`
supplies its actual endpoint; its published agent guidance should explain issue
submission and review through that plugin.

## Owner maintenance

The private repository owner controls cleanup and history compaction. Run from
its source checkout, using the same configured ticket endpoint:

```sh
nix run .#publicate -- ticket-compact --force --push
nix run .#publicate -- ticket-compact --force --drop-resolved --push
```

`--force` explicitly requests owner maintenance. Compaction keeps the current
ticket tree and replaces its history with one parentless commit. `--drop-resolved`
also removes applied and inapplicable records. Kept UUIDs and fingerprints stay
fixed. A later identical report can create a new ticket after removal.

The owner push uses an expected-value lease for the ticket branch. Concurrent
queue changes stop compaction so the owner can refresh and retry. Agents resume
ordinary submissions on the new tip; detached reviews retain their original
snapshot and reconcile through record IDs. Git server permissions determine
who can append and who can force-update the branch. Configure branch protection
to give contributors append access and reserve force updates for maintenance.

## Review current applicability

Requires Bash, Git, Nix with flakes, a private Git endpoint, and a Publicate app
named `publicate`. Install the public [review template](../templates/review.sh.in)
in the private project, preserving an existing script:

```sh
cd /path/to/private-project
mkdir -p publicate
if [ ! -e publicate/review.sh ]; then
  install -m 755 /path/to/publicate/templates/review.sh.in publicate/review.sh
fi
```

An agent already running in Codex, Claude or another environment can choose a
temporary directory and run:

```sh
review_dir=$(mktemp -d "${TMPDIR:-/tmp}/publicate-review.XXXXXX")
cd "$review_dir"
/path/to/private-project/publicate/review.sh
```

`PUBLICATE_FLAKE` selects a different app or pinned tool input. The script fetches
the private ticket branch and creates a fresh detached worktree beneath the chosen
directory. The default parent is `$TMPDIR`, falling back to `/tmp`. An optional
directory argument selects another parent. The worktree shares the source
repository's Git object store and materializes ticket files plus local review
instructions. Repeated runs preserve prior worktrees and create fresh ones.

The returned `instructions` path identifies `.publicate/REVIEW.md`; read it along
with `tickets/*.json`. By default, evaluate open reports against the current source
checkout, including its working-tree changes and applicable project instructions.
The agent establishes whether a report still applies, implements applicable fixes
in that source checkout, and updates ticket status and resolution here. Review
preparation launches a worktree; the existing agent performs the semantic review.
Unresolved reports stay open. Code changes stay in the source checkout.

Synchronize reviewed records with the returned worktree path:

```sh
cd /path/to/private-project
nix run .#publicate -- ticket-sync /path/to/ticket-worktree --push
```

Synchronization validates records and merges against the original ticket snapshot
and the current queue. A failed synchronization preserves the worktree for the
agent to resolve and retry. The default retains the local worktree; once finished,
remove it with `git worktree remove --force /path/to/ticket-worktree` after preserving or
synchronizing its review changes. The local `.publicate/` instructions are generated
context and stay outside the ticket snapshot. Queue updates require the ticket
branch to be free of attached worktrees; the review command uses detached worktrees.
